# Dashboard prototyping

Produce reviewable alternatives and a selected prototype at the least fidelity that can answer the design question. Own both rough exploration and realistic interaction; do not create separate sketch and build skills. Read [handoffs](../../references/workflow-contract.md) before starting. Keep this stage's author checks distinct from independent evaluation.

1. **Establish the current design input.** Read the brief revision, authorized scope and actual fixture/sample. Confirm decision, data-meaning, viewing and must-preserve workflow constraints. Make consequential workflow changes explicit and resolve conflicts with agreed requirements before replacing them. If no brief exists, recover a minimal working brief from available evidence and label assumptions; do not force discovery ceremony for a settled request. Route consequential unknown goals/semantics to dashboard-discovery and keep dependent work provisional. Stop when the prototype's purpose, fidelity and evidence basis are explicit.
2. **Explore structural alternatives.** When organization is unresolved, make a small number of materially different rough sketches (usually two), such as exception-led versus entity-comparison-led. Compare their decision paths and information tradeoffs, not cosmetic variants. Use text, diagrams or rough screens as appropriate. Reuse a settled choice rather than manufacturing alternatives; state the reason. Select a reversible working direction within the request's authority, asking only for choices that materially change the work.
3. **Build the required fidelity.** Use realistic authorized or synthetic data with long labels and representative missing, partial, stale, invalid and empty states. Use [data meaning](../../references/data-meaning.md) for comparisons/scales; [monitoring/interaction](../../references/monitoring-interaction.md) for live updates, pause/resume, alerts and exploration; [service semantics](../../references/service-semantics.md) only for service status. Preserve exact values, evidence quality and context. Do not invent history or thresholds. An interactive question requires working controls/state changes, not painted controls; a static question need not incur an application build.
4. **Check the artifact as its author.** Use [verification](../../references/verification.md) for initial desktop/narrow actionability, component feasibility, actual modal update exposure, responsive semantic relationships and focused runtime checks. Label unimplemented behaviors and tests not run. Do not call these author checks independent review or evidence of user efficacy. Stop when the artifact can demonstrate its declared purpose and its limitations are visible.
5. **Package the handoff.** Deliver sketch paths and selection rationale, the prototype manifest, exact fixture/data revision, artifacts/run instructions, expected supported interactions and a factual author-check log. Keep subjective rationale out of the independent evaluator's minimal packet. Hand that packet to dashboard-evaluation when review is requested. Preserve prior evaluated versions; link a revision to the findings it addresses.

After evaluation, repair authorized implementation defects here; route changed tasks, metrics or policies back to discovery. Do not optimize merely to a hidden scoring key. Production implementation, specification and ticket creation remain downstream: reuse available to-spec then to-tickets when requested. A local prototype does not authorize installation, live data access, deployment or publication.

## Visual refinement

Read [visual-craft.md](../../references/visual-craft.md) for composition, typography, spacing, semantic color, responsive behavior and browser inspection. Apply it to the existing task and design system, not as a cosmetic template. Record the visual thesis and review actual target viewports; do not trade data honesty or preserved workflows for polish.
